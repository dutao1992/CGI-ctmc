# 车载数据容量与自动清理

## 目标
评估现有数据增长，服务器文件系统使用率达到 80% 后定期删除最早积累的车载数据。

## 完成标准
每小时检查；80% 触发、75% 停止（后者为防反复触发的默认值）。保护最近 24 小时、当日目录、打开中的文件和未处理积压。删除原始日志及对应采样，回收 SQLite 空闲页；保留设备配置和审计记录。生产低于阈值时零删除。

## 禁止事项
不改、不重启 9000 接收器；不清理其他质检业务、系统日志、备份或代码版本。不在生产伪造高占用做删除测试。不跟随符号链接，不删除白名单外文件。

## 执行步骤
1. 读取 df、原始日志、数据库、接收器和定时任务现状，按真实采样估算连续工作日增量。
2. 实现文件白名单、共享采集锁、持久删除标记、分批删除和增量空间回收；扩展现有测试。
3. 在低占用时备份并迁移数据库为 incremental auto_vacuum；仅短暂停止新车载解析服务，TCP 接收继续。
4. 部署独立 systemd oneshot/timer，执行一次正常检查，核对零删除及定时器下一次触发。
5. 更新页面留存说明、运维文档和验收证据。

## 验收方法
原有 21 项测试不减少；新增测试覆盖阈值、最旧优先、正在打开/近期/未读/越界保护、崩溃重试、不重导入、实际文件缩小。生产检查服务状态、数据库 quick_check、定时器、删除计数、接收器 PID 和源码哈希。

## 风险
清理后的数据不可恢复；默认留存不是运输监管法定保留期承诺。车载旧数据不足时只能告警，不能保证整体磁盘下降至 75%。文件按接收日期清理，最近 24 小时和当日保护可能保留更久。任务每次限时，超时下次续作；容量压力持续时需扩容。数据库迁移需额外空间，先做余量检查和一致性备份。

## 回滚方案
停用 ctmc-vehicle-retention.timer 及 service 可停止后续删除。发布失败恢复旧 current 及旧车载 service。迁移保留一致性 SQLite 备份；非必要不回灌以免覆盖新采样，增量回收模式与旧代码兼容。已经按策略删除的数据无法由停用任务恢复。
