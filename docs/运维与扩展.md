# 线上运维与扩展

## 本次部署

- 独立服务：`ctmc-vehicle.service`，回环地址 `127.0.0.1:8790`。
- 当前版本：`/srv/ctmc-vehicle/current` 指向最近验收的版本目录（用 `readlink -f /srv/ctmc-vehicle/current` 查询）。
- 数据：`/srv/ctmc-vehicle/data/vehicle.sqlite`，SQLite WAL；游标与测量写入在同一个事务。
- 只读原始源：`/srv/chcnav-cgi430/logs/raw/YYYY-MM-DD/*.log`。
- 现有门户仍为 `/srv/ctmc-quality/current`；挂载只改认证注册、nginx 路由和门户入口，不改原业务模块文件。
- 挂载备份和回滚：`/srv/ctmc-vehicle/backups/mount-20260826-155514/`。
- 服务目前以 root 读取原来 root 专属的原始目录，不更改原接收日志权限；systemd 将全系统设为只读，只允许写新数据库目录，并禁用提权/系统能力，限制内存 512 MB 和 CPU 80%。

## 日常检查

```bash
systemctl status ctmc-vehicle.service --no-pager
curl -f http://127.0.0.1:8790/healthz
journalctl -u ctmc-vehicle.service -n 50 --no-pager
df -h /srv
ss -lntp | grep -E '8790|9000'
```

采集器失败会写日志并通过 healthz 返回 503；设备离线由最后设备时间和文件写入时间共同判断，30 秒未更新或设备时钟相差超过 60 秒不标在线。接收文件没有每帧接收时间，因此不提供伪精确的网络延时指标。

服务心跳正常不代表设备在线，也不代表 RTK 固定解。定位固定解占比是原始采样占比，不是厘米精度保证。保留位告警单列，不按真实硬件故障报警。

## 回滚

```bash
bash /srv/ctmc-vehicle/backups/mount-20260826-155514/rollback.sh
```

脚本恢复本次修改前的门户入口、认证文件和 nginx 配置，校验配置后重启平台 API、reload nginx，并停用新服务。**不会恢复整个账号库、不会删除新采样库，也不会触碰 9000 接收器。**备份的账号库用于取证，不应直接覆盖正在使用的数据库；新增 vehicle 权限键即使留在账号记录中也没有旧平台入口或路由。

## 新设备

1. 在设备端配置含 SN 的 GPCHCX 输出，并指向现有接收地址。不要单凭公网来源 IP 绑定设备。
2. 收到首个校验通过的 GPCHCX 后自动建档。为设备补充车辆编号、项目/车队，设置合适的业务速度阈值。
3. 固定安装，确认手册所述姿态参考系、轴向、单位、时间、定向初始化和 RTK 状态，再启用“安装已确认”。默认关闭姿态/冲击业务预警。
4. 道路实测：已知路段距离、直行加减速、转弯和停车，核对轨迹、速度、姿态与事件。没有这个步骤，不把候选事件用于安全执法或控制车辆。
5. 设备真实身份鉴权、车队级访问控制和每设备原始数据带宽配额属于下一阶段扩展；目前提供模块级访问控制和逻辑 SN 隔离。

## 容量与下一阶段

接收器本身不变，由独立 `ctmc-vehicle-retention.timer` 每小时检查：磁盘达到 80% 后清理最早车载数据至目标 75%，保护至少最近 24 小时和活动文件。仅清理车载原始日志、关联采样及过期事件；不动其他业务、备份、配置与审计。页面显示检查回执及异常；超过 90 分钟无回执提示检查定时器。详见 [存储清理说明](存储清理说明.md)。

## 长时间查询

`point_rollups` 是从原始采样、v5 三轴运动状态和过滤决策确定性生成的 60 秒派生表，另有 10 分钟父桶。超过 6 小时的图表查询读取完整聚合桶，查询首尾继续读取原始点；桶计数与原始范围计数不一致时自动回退原始路径。均值按有效样本数加权，最小/最大包络、运动状态和三轴比力合成模长的 min/max/sum/sum-of-squares/count 一并保留，不能把派生表当成原始证据。部署时运行 `deploy/prepare-rollups.py` 校验当前版本两层覆盖（v5 对应 rollup 版本 504）；仅在计数或版本不一致时全量重建。当前聚合已完整时不在服务停机窗口重复执行耗时的全库 `quick_check`；实时采样、质量重算和存储清理都会同步更新或重建受影响的桶。

查询缓存位于服务进程内，最多 16 项；实时窗口 10 秒、历史窗口 60 秒。缓存不写入浏览器公共缓存，不跨权限边界；迟到采样和外部清理通过范围失效或 `query_cache_epoch` 失效。数据质量页的“长时查询聚合”应显示版本桶全部有效，异常时可停止解析服务后重新执行：

```bash
cd /srv/ctmc-vehicle/current
/usr/bin/python3.11 deploy/prepare-rollups.py --db /srv/ctmc-vehicle/data/vehicle.sqlite
```

需要独立核验 SQLite 完整性时，应在业务低峰显式执行（百万级数据库可能持续数分钟）：

```bash
cd /srv/ctmc-vehicle/current
/usr/bin/python3.11 deploy/prepare-rollups.py --db /srv/ctmc-vehicle/data/vehicle.sqlite --verify-current
```

建议扩展顺序：独立数据盘与备份 → 按设备/日期分区与多分辨率聚合 → 压缩原始归档和经批准的保留期 → VPN/认证网关 → 车队级授权 → 地图服务保障 → 有明确业务规则的围栏与路线偏离。保留现有 SN、UTC 时间和规则版本契约，可迁移到 PostgreSQL/Timescale 等时序存储而无需更换页面工作流程。

## 源码一致性

现网门户和本地 `quality-platform` / `failure-analysis` 有本次任务以前的差异（如密码长度和已有安全增强）。本次生产发布基于捕获的现网文件精确补丁，避免顺带覆盖这些差异；本地源文件同步新增了 vehicle 注册和入口。以后使用全量门户部署脚本之前，必须先确认这些既存差异，不能以本次通过的模块验收代替全量发布回归。
