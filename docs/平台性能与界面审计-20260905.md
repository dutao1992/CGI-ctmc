# quality-ctmc.cloud 性能与界面审计

审计日期：2026-09-05，北京时间。基线结论是优先优化车载查询中的静止轨迹锚点处理，其次修复重复查询与缓存失效，再做按页加载和界面收敛。上述首批修复已完成并上线，长时筛选的主要瓶颈已重新复测。

本报告保留优化前基线，并补充实施后的代码、测试、线上版本和只读性能复测。原始采样与数据库内容未改写，工作区原有未提交修改保留。

## 已核实范围与边界

- 车载线上 release：`/srv/ctmc-vehicle/releases/20260905-214811`。`static/app.js`、`static/index.html`、`static/style.css`、`vehicle/store.py`、`vehicle/aggregate.py` 均与当前工作区 SHA-256 一致；页面脚本指纹为 `c9923505583c`，样式指纹为 `0a624d747550`。
- 平台 release：`/srv/ctmc-quality/releases/20260903-091310-ablation`。核对公开主页、实际引用 JS、共享 nginx 路由与服务状态；其他业务模块没有逐项做登录后的流程和性能验收。
- 查询测量直接在生产主机的独立 Python 进程中运行线上查询实现。数据库用 `mode=ro` 和 `PRAGMA query_only=ON`，绕开会初始化表结构的 `Store.__init__`；串行、低调度优先级、有总超时。测量不是并发压力测试。
- 数字包含查询内部计算，**不包含认证、HTTP 排队、网络传输、浏览器 JSON 解析和绘制**。首次指该独立进程的应用缓存未命中，操作系统文件缓存未控制；并非磁盘冷启动，也不是 p95。
- 已登录桌面 Chrome 刷新到当前版本，确认 96 小时快捷筛选从“正在查询”进入“已应用”，返回 724,007 条采样、62 个振动时间桶、速度/振动曲线和地图节点；首屏无数据时也能明确清空旧结果。浏览器状态树显示速度曲线和振动曲线位于地图之前。该次状态树未作为高精度计时器，性能数字以生产机只读分段复测为准。

## 优化清单与优先级

### P0：静止轨迹处理反复扫描整条轨迹

位置：`vehicle/aggregate.py:322`、`:359`、`:541`。

96 小时复测总耗时 30.735 秒，其中 `_anchor_stationary_track()` 为 **26.850 秒，占约 87.4%**；总共 7,829 个轨迹点、13,254 个运动状态区段，其中静止区段 6,302 个。聚合 `add()` 合计仅约 67 毫秒。

每个静止区间都寻找前后运动点，并再扫描轨迹替换区间内静止点坐标。成本随“静止段数 × 轨迹点数”增长。虽然原始采样已聚合，这一步仍可把请求拖到几十秒。

建议：预建运动点时间索引；用二分定位前后运动点与区间边界，或按时间双指针扫描；每个轨迹点只更新必要次数。保持锚点候选的置信度选择、2 米容差、连续区间合并、断档与跳点规则完全一致。不要通过删减静止段、平滑速度或改变定位语义换取速度。

验收与结果：同一数据、同一查询的锚点坐标、`position_source`、断线、首尾点、里程及事件回归通过；96 小时锚点阶段 103.6 毫秒，10 天完整查询 4.979 秒。仍保留 0.5 秒锚点预算作为后续回归上限。

### P0：没有新数据时仍重复查询，缓存寿命与刷新频率不匹配

位置：`static/app.js:195`、`:903`，`vehicle/store.py:114`、`:585`、`:646`。

默认每 15 秒刷新。后台查询缓存对结束时间接近设备最新采样的请求只保留 10 秒，即使设备早已停止上报、查询参数完全相同，下次刷新时也已过期。“截至现在”模式的起止时间持续变化，还会不断生成不同缓存键。查询开始会清空全部图表，进一步造成闪烁。

建议：先核对设备与数据版本；无新采样、无规则/质量投影变更时不重跑重查询、不清图。已封闭历史范围用数据版本和规则版本失效，保留有界内存与兜底 TTL。实时查询保持准确的所选时间轴；只重算尾部变化，不能静默改写用户指定的起止时间。

验收与结果：自动跟随现在先比较设备 `last_t`，无新样本不清图、不发查询；新增 Node 回归覆盖“相同 `last_t` 跳过、出现新样本后查询”，迟到采样和质量版本仍通过原有失效路径。后端 TTL 仍是兜底，不把 `last_t` 作为永久缓存条件。

### P0：曲线请求被轨迹与 FFT 诊断阻塞

位置：`static/app.js:211`，`vehicle/store.py:566`、`:585`，`vehicle/aggregate.py:487`。

所有页面共用完整 `/api/query`，惯导分析也必须等待地图轨迹锚点处理、振动诊断与事件返回。10 天响应中轨迹占 3,637,579 / 3,949,608 字节，约 **92.1%**；惯导曲线本身仅约 99 KB。振动诊断并非单独 FFT 运算，还包含原始点读取、候选窗查找和分析；密集小时该部分耗时 2.72 秒。

建议：按页面需要拆分结果。惯导页面先返回信号、质量摘要和必要事件标记；总览先返回速度、振动趋势和摘要，地图轨迹与 60 秒诊断频谱分区加载。可提供 `include` 参数或独立接口，但不能只把当前完整大查询复制成多个接口、重复计算几遍。共享聚合结果，针对轨迹和诊断分别缓存。

当前结果：振动候选窗口已合并，96 小时与 10 天查询分别降至 3.899 秒和 4.979 秒；完整的按页面拆分接口、未展开诊断不计算 FFT 仍是后续优化项，当前请求仍返回完整结果以保持接口兼容。

### P1：快速换筛选仍要等待旧查询

位置：`static/app.js:195`、`:211`，`vehicle/server.py:131`。

现有 request 编号会丢弃旧结果，但单一 `queryPromise` 必须等待旧请求完成，才能执行最新待处理请求。旧的 10 天查询若已耗时几十秒，切回短窗口也会继续等待。服务端仅允许两个重查询槽位，最长排队 15 秒；重复计算还会影响其他使用者。

建议：保留“最后一次选择生效”和请求合并；增加请求取消/过时检查。浏览器 `AbortController` 只能中断客户端等待，不应声称自动停止了 Python 计算；后端需要在可中断的计算阶段检查任务是否过时，或采用有界任务调度。相同缓存键的并发未命中合并为一次计算。

验收与结果：浏览器旧请求在客户端被中止，`request` 序号和设备隔离回归通过，旧结果不会覆盖新筛选；服务端仍以两个查询槽位限流，未增加线程竞争。后端计算取消点尚未加入，客户端中止不等于停止已在运行的 Python 计算。

### P1：隐藏内容仍在生成，图表更新工作可进一步减少

位置：`static/app.js:237`、`:440`、`:613`、`:754`、`:900`。

每次查询先运行 `renderEvents()`，即使当前看的是总览或惯导，也构造完整事件列表和 Top10；事件列表上限 2,000 行。图表已有实例复用和每帧两张的分批绘制，但最终仍绘制全部 12 组信号，且统一 resize 包含隐藏图表。`setOption(..., true)` 后又立即 `resize()`，筛选前还会 `clear()`。

建议：事件页进入时再生成列表，并分页；信号图按可见区域优先、屏外延迟绘制。只有数据版本或尺寸变化时更新对应图表，尺寸未变不重复 resize。保持鼠标联动、缩放、报警线和振动 tooltip 原有行为。

这一项是代码确认的额外工作，浏览器主线程具体节省多少尚未实测。不要将它列为已测得的 30—88 秒主因。

### P1：精简车载界面，把曲线放到更靠前的位置

依据：线上当前 release 的 `static/index.html` 与 `static/style.css`；登录后的桌面 Chrome 已核对首屏和 96 小时曲线顺序，移动端仍未做专项验收。

| 现状 | 建议 |
|---|---|
| 大标题口号、英文眉题、介绍文案与多层状态占据顶部 | 改为“车载数据 / 运行总览”紧凑标题，状态合成一行 |
| 8 个快捷范围 + 终点选择 + 两个日期框 + 跟随选项 | 主栏保留设备、常用范围、应用；更多范围与自定义日期放展开区。保留“截至现在/最新采样”的明确含义 |
| 采样新鲜度、查询时段、提示、过滤说明分成多条横幅 | 一行“已应用范围 / 最新采样 / 覆盖率”；异常时才扩展提示，技术细节进入数据质量或帮助 |
| 地图与最新状态大块排在曲线前面 | 总览让速度与振动趋势更靠前；地图与曲线可切换主视图，保留地图回放入口 |
| 设备快照、指南针、英文编号、算法说明持续展示 | 最新状态折为摘要或侧抽屉；算法说明集中在图表帮助中，清楚区分“最新状态”和“筛选时段” |
| 惯导页默认铺满 12 组图和判定图 | 提供“常用 / 全部 / 自选参数”，默认速度、姿态、振动/冲击相关内容；保留专业参数可达性 |
| 不少辅助文字只有 8—10px | 通过减少重复内容腾出空间，再提高关键标签字号；不要靠缩小字体压缩页面 |

建议的首屏顺序：紧凑标题 → 一行筛选 → 已应用范围和关键状态 → 核心指标 → 速度/振动曲线。完整频谱、算法解释和不常用参数按需展开。目标是在常用桌面视口不滚动即可看到首张有效曲线，须登录后做截图与交互验收。

### P2：平台入口不宜被健康检查完全锁住

证据：公开线上 `/assets/index-vehicle-2b474d75086d.js` 中，入口可点击条件是 `href && canAccess && health === 'online'`；统一 `system-health` 请求失败会把全部模块标为 offline，入口变为不可点击的 `div`。

建议：有权限的入口保持可进入，健康检测用“检测中/暂无法确认/已知异常”提示；无权限仍禁止访问，后台认证照常执行。为检测提供重试，区分观测失败与业务真实故障。此处只核对前端逻辑，未测量该健康接口的认证后耗时。

平台首页已经采用五个模块入口和简短标题，不应把旧宣传型首页当作当前页面重新大改。公开主 JS gzip 约 57 KB，已具备指纹和长期缓存，优先级低于车载计算。

### P2：缓存与观测基础设施补齐

- 车载静态资源由 Python 发送 `private, max-age=300`；nginx `/vehicle/` 的 `^~` 路由使通用静态资源正则不适用于它。已有资源指纹，可研究对不含用户内容的版本化 vendor/JS/CSS 延长私有缓存并做条件请求；HTML 保持更新可见，认证和权限边界不变。ECharts 文件原始大小约 1.12 MB。登录后的实际缓存命中率待测。
- 车载请求经历 nginx `auth_request` 和应用内 `authorize()` 两层鉴权调用。代码证实存在两次认证链路，耗时未量化；先记录时间，再判断是否需要减少重复工作，不能直接删除任一边界或信任可伪造的外部请求头。
- 页面展示的 `query_ms` 不包含排队、认证、序列化、传输及绘图；当前 nginx access log 使用默认格式，未显式加入请求/上游耗时。建议增加分段计时与请求 ID，把首图可见和全部可交互分别记录，日志不记录 cookie 或完整敏感请求正文。
- 服务器快照为 2 CPU、约 1.84 GiB 内存、数据库 1.9 GB、磁盘使用 80%/可用 7.8 GB。存在约 511 MiB 已用 swap，但短时 vmstat 未见持续换入换出，不能据此断言换页是瓶颈。先完成算法优化，再评估容量；审计未做清理或扩容。

## 建议实施顺序与验收

1. 对静止锚点建立时间索引，保留输出语义；先验证 96 小时和 10 天。
2. 修复无变化重复刷新、版本化缓存和相同请求合并。
3. 曲线与轨迹/频谱按需加载，快速切换只处理最新查询。
