# quality-ctmc.cloud 全平台优化审计

2026-09-06。结论：优先修复会话过期反馈和车载数据版本检测，再减少追溯启动数据与各看板隐藏内容的加载。当前证据不支持先扩容或整体重写前端。

实时版本：平台 `20260903-091310-ablation`，追溯 `20260903-091310-ablation`，车载 `20260905-214811`。平台 API、Web、追溯、车载服务均 active，车载 healthz 正常。服务器内存 1888 MiB、可用 845 MiB，swap 已用 403 MiB，磁盘 80%、可用 7.7 GiB；这一时点不足以判断持续内存压力。

先前 Chrome 登录会话失效时，车载旧页出现 HTTP 401。用户重新登录后，已补查门户五入口、机组搜索及详情抽屉、失效分析已有报告、追溯单点登录与查询工作区、装配中心切换、车载空范围状态。尚未完成端到端延迟采样和窄屏视觉验证。下述“代码确认”与“浏览器实见”分开列出，不把源文件大小当作下载耗时，不把建议收益当作已测提升。本轮未修改业务代码或发布线上版本。

| P2 | 静态资源缓存规则不统一 | nginx 的受保护模块 `^~` 路由绕过通用静态扩展名缓存规则；车载已有指纹但 max-age 300 | 在各受保护模块内为带版本资源设置适当私有缓存与条件请求，HTML 保持更新可见；不得移除模块授权 |

车载版本检测是上次优化的遗漏。后端缓存失效无法替代前端发起新查询：只要前端仅凭 `last_t` 跳过，就可能持续显示旧结果。上次报告中“迟到采样和质量版本仍通过原有失效路径”的措辞不能视为该场景的端到端验收通过。

机组 JSON 的 `generatedAt` 是 `2026-06-23T09:07:32+08:00`。这是文件自报生成时间，不证明数据错误，但应显示“历史快照/数据日期”，不能只靠绿点暗示实时。登录后页面已有快照说明和生成时间，应保留，不应误判为缺少日期。

## 界面精简方案

以下结合部署代码与登录后无障碍树复核；布局改造仍需桌面与窄屏截图验收。

- 门户：保留五个模块入口；当前卡片已经精简为编号、名称与状态，保留此结构；权限不足与检测失败分开表达。
- 机组评价：默认“风险摘要 → 搜索与常用筛选 → 机组列表”；地图与方法说明按需展开；统计分析已有展开/收起机制，不重复开发。现有加载更多和详情抽屉保留；输入搜索加约 150 ms 防抖并预建搜索文本。
- 质量追溯：现场模式首屏以扫码、当前订单及待绑定项为主；管理、主数据、容量和统计按权限及页面延后加载；减少每次扫码后全工作区重绘。
- 装配看板：统一中心选择器和检验状态，收敛为一张明细列表；当前中心才生成图表；保留当前已显示的数据日期，技术说明和导入说明折叠。
- 失效分析：现有新建/历史入口、选填资料折叠、报告摘要与目录已经具备，应保留；进一步减少模型与平台技术文案，不把已实现功能列为待开发。
- 车载：延续速度/振动优先顺序，继续合并顶部重复状态与算法文案；地图和诊断频谱按需加载，专业参数用常用/全部切换。

## 验收与建议实施顺序

1. 修复会话状态和车载修订号；统一机组快照按钮的可访问名称。
2. 精简追溯首包和机组数据载入；给入口健康探测隔离故障。
3. 本地化装配看板依赖、隐藏内容延后绘制，再统一页面标题与筛选布局。
4. 固定设备/网络采集首屏、筛选到结果、首图与可交互时间各至少 20 次，报告中位数/p95；同时记录响应大小、缓存命中、长任务与错误，不收集 cookie、密码或原始业务正文。
